**Origem:** [PR #248](https://github.com/moxi-edtech/moxi-edtech/pull/248), execução [39876639827](https://github.com/moxi-edtech/moxi-edtech/actions/runs/39876639827) (22/10/2026 em São Paulo; execução UTC 23/10). ## CC-014 · taxa distribuída, com o limitador real

A instalação da função `check_public_rate_limit` **não é um mock**: `prepare_real_rate_limit_fixture.py` extrai literalmente a definição SQL de `20270529123000_admissoes_public_protocol_and_vault_rate_limit.sql` para a base temporária. O contador usa linha bloqueada por `FOR UPDATE`, partilhada entre processos e conexões.

| Prova (2 processos independentes, conexões simultâneas) | Resultado |
| --- | ---: |
| Operador A, 50 pesquisas em paralelo | **30 permitidas, 20 bloqueadas** |
| Operador B, mesma escola, 12 pesquisas | **12 permitidas, 0 bloqueadas** |
| Outro utilizador a consultar alunos de escola alheia sob RLS | **0 resultados** |
| Chamadas extra ao Supabase só para verificar taxa | **0** (limite dentro da mesma RPC) |

A rota deixa de chamar `allowRosterRequest` em memória. O helper legado persiste apenas para não eliminar regressões antigas; **não integra o caminho de execução**. Limites de IP, WAF e quotas globais não foram avaliados.

## CC-015 · planos reais de PostgreSQL com dados totalmente sintéticos

Fixture com **3 escolas, 24 turmas adicionais e 6.700 novos alunos fictícios**, matrículas, mensalidades parciais e em atraso e eventos de documentos; turma-base de 55/50 mantida. `EXPLAIN (ANALYZE, BUFFERS)` sobre pesquisa, ordenação, filtro, contagem e RPC. Cinco tempos de execução (ms), **na ordem das consultas SQL do ficheiro**, não são p95:

| Consulta | Antes dos índices | Depois dos índices |
| --- | ---: | ---: |
| Contagem por classe/ano | 56,212 | 56,988 |
| Ordenação por nome na classe | 59,791 | 60,790 |
| Contagem de eventos documentais | 12,143 | 11,763 |
| RPC operacional, filtro `ambos` e prioridade | **545,078** | **128,821** |
| RPC histórica nome A–Z | 74,602 | 67,262 |

A migration `20271022140000_command_center_perf_indexes.sql` é **aditiva** (índices em matrículas activas e candidaturas/escola/ano). O CI aplica, reaplica, reverte exclusivamente no PostgreSQL descartável, verifica ausência dos índices e reaplica. Nenhuma migration ou reversão foi aplicada no Supabase.

## CC-016 · p50/p95, tamanho de payload e orçamento de chamadas

Amostragem de **3 séries × 8 chamadas por versão**, na mesma turma de ~313 estudantes fictícios, com arranque de conexão e processo `psql` incluído na latência. O baseline é a RPC `command_center_roster_keyset_v2`, e a versão candidata `command_center_roster_operational_v1` após os índices.

| Métrica (PostgreSQL de CI, não browser) | Antes | Depois |
| --- | ---: | ---: |
| p50 (ms) | 48,21 | 76,65 |
| p95 (ms) | 54,76 | 80,02 |
| Tamanho médio da resposta (bytes) | 5.712 | 7.682 |
| Número de consultas para carga equivalente | 24 | 24 |
| Diferença de consultas | | **0** |

**Regressão observada:** p95 +25,26 ms e resposta +1.970 bytes. A RPC nova devolve indicadores adicionais; estes números **não sustentam afirmar que a nova consulta é mais rápida para nomes A–Z**. O ganho verificado refere-se ao plano do filtro operacional `ambos` quando se acrescentam índices, não à comparação de versões heterogéneas. O campo `requestsPerHourForMatchedWorkload` do JSON é uma **projecção de 24 operações equivalentes por hora**, não telemetria observada durante uma hora. A API não acrescenta chamadas de polling.

**Gate de desempenho antes de produção:** comparar na réplica fiel, com dados sintéticos de distribuição realista, browser autenticado e tráfego do mesmo roteiro. Se o p95 de produção exceder o orçamento aprovado, optimizar a avaliação das flags depois da paginação para sort A–Z sem alterar a semântica das contagens.

## CC-020 · 400 operações simuladas no React real, sem dados pessoais

A fixture do componente real de Turma (APIs simuladas) efectuou **110 selecções e retornos do Balcão, 170 mudanças de filtro e 120 mudanças de ordenação**, seguida de intervalo com a aba em segundo plano.

| Medida | Antes | Depois de 400 operações |
| --- | ---: | ---: |
| Heap JS do Chromium | 22.061.992 bytes | 26.169.225 bytes |
| Nós DOM activos | 428 | 136 |
| Entradas de cache React Query | 2 | 7 |
| Timers activos | 3 | 7 |
| Intervalos activos | 1 | 1 |
| Listeners globais activos (balanço aproximado) | 5 | 5 |
| Requisições simuladas à API | 1 | 6 |
| Requisições durante aba oculta | | **0** |
| Dados do aluno persistidos em Local/Session Storage | | **Não** |

O crescimento de heap (~4,1 MB) manteve-se dentro da margem explicitada no teste. A regra de retenção de estado dos cinco exploradores continua limitada a 40 vistas e 24 breadcrumbs. Não confundir 400 operações sintéticas com uma sessão humana autenticada de oito horas. Os ouvintes ligados a nós DOM reclamados pelo garbage collector não são contados como listeners globais: a prova indirecta é dada pelo heap/nós DOM.

## Gatilhos pendentes e riscos

1. **CC-001** (proprietário): reconstrução/replay de todas as migrations e políticas reais em base descartável. Esta fixture compõe migrações canónicas pertinentes e RLS de contrato; não alegar equivalência estrutural total.
2. GoTrue de teste, fluxo autenticado em cinco vistas, isolamento organizacional por polo a partir de vínculo canónico e sessão humana longa: bloco D/decisão de domínio.
3. Leitor de ecrã NVDA/VoiceOver e aceitação das regras da escola: aprovação humana separada.
4. O aumento de p95/bytes no baseline A–Z é um risco quantitativo que precisa de comparação no ambiente final antes de autorizar release.

Comandos reproduzíveis: workflow `Command Center C Load and Memory` da PR. Nenhum comando `supabase db push`, merge ou deploy é autorizado por este relatório.
